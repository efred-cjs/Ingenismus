2. CONSOLIDACION DEL FRONTEND
=============================

La aplicacion activa es React/Vite y se inicia con npm run dev. Antes de esta
etapa el prototipo de Web_interface (prueba.html, ingenismus.css y
ingenismus.js) accedia Firebase directamente desde el navegador y mantenia
su propio ciclo de lectura y graficas Chart.js. Se retiro esa interfaz
duplicada: sus funciones utiles (seleccion de sensor, consulta, conteo,
ultima lectura y graficas de acelerometro/giroscopio) estan resueltas por
frontend/src/App.jsx, frontend/src/services/mediciones.js y
frontend/src/components/GraficaLecturas.jsx, con el mismo snapshot de API.

ingenismus.css y ingenismus.js quedaron integrados bajo esos nombres en
frontend/src. El HTML de prueba anterior en frontend/src/prueba.html era una
copia independiente que apuntaba a recursos ausentes en ese directorio; no
contenia funciones adicionales. Se retiro tras respaldarlo. No se carga HTML
externo ni se accede a Firebase desde el navegador.

Componentes visuales repetidos que se resolvieron:
- Se quitaron participantes y sesiones estaticos que no procedian del backend.
- Un unico estado de API/Firebase, modo y sesion alimenta Inicio, Estadisticas,
  Visualizacion, Resultados y Recoleccion.
- La tabla de lecturas se comparte entre Visualizacion y Resultados; cambia
  solo el filtro (sensor o sesion) y no consulta otra fuente.
- Vision artificial se muestra como No configurada; no existe servicio de
  vision en este repositorio y no se presenta como activo.

3. FLUJO DE DATOS Y CONTRATO
============================

ESP32 o backend/simulador_wifi.py
  -> POST /mediciones en Flask
  -> validacion de tipo, sensor, modo y sesion activa
  -> Firebase Realtime Database /mediciones/<id>
  -> GET /panel cada dos segundos por el cliente central
  -> filtros compartidos por modo y sesion
  -> tarjetas, tabla, estadisticas y graficas.

El snapshot GET /panel incluye firebase, modo, sesion_activa, sesiones
(ultimas 50) y mediciones (ultimas 300). La respuesta existente GET
/mediciones?limite=N se conserva. El proxy Vite traduce /api a Flask.

Campos originales de cada lectura: sensor_id (1 o 2),
aceleracion_x/y/z y giroscopio_x/y/z (enteros raw counts). El backend agrega
fuente (esp32 o simulado), modo, sesion_id y fecha_servidor (timestamp Unix
en milisegundos asignado por Firebase). El frontend conserva campos y valores
originales; muestra raw counts y fecha local del navegador. Registros
historicos sin fuente se interpretan como ESP32. Los registros previos sin
sesion_id se consultan en una opcion separada "Historico sin sesion"; nunca
se mezclan con una sesion identificada.

4. MODO Y SESIONES
==================

El modo se persiste en Firebase en estado/modo. Valores permitidos: esp32 y
simulado. Para cambiarlo se requiere no tener una sesion activa (PUT /modo con
{"modo":"esp32"} o {"modo":"simulado"}). La interfaz bloquea el selector
mientras una sesion esta abierta.

POST /sesiones crea un UUID, registra inicio/modo/estado y guarda su ID en
estado/sesion_activa. Puede recibir prueba=promedio o prueba=tea. Los botones
Iniciar prueba de ambas vistas aseguran el modo esp32 y abren la sesion con
su tipo; a partir de ahi las lecturas entrantes del firmware quedan asociadas
a esa prueba. POST /sesiones/cerrar marca fin, finaliza la sesion y elimina
el puntero activo con delete() (Firebase no acepta un None como valor raiz);
los registros historicos no se borran. POST /mediciones rechaza HTTP 409 si
no hay sesion activa o si la fuente no coincide con el modo actual. El
simulador envia fuente=simulado. El firmware no necesita cambios: la API
considera ESP32 las lecturas que no declaran esa marca.

Cada sesion registra su modo. Graficas, conteos, tabla y lecturas recientes
filtran tanto por modo como por una sola sesion; si no hay sesion activa, no
se atribuyen lecturas a una sesion actual. El selector permite consultar
sesiones anteriores sin cambiar sus datos. El snapshot limita el historial a
300 lecturas y 50 sesiones recientes; Firebase conserva los registros
historicos completos.

5. VISION, ESP32 Y FIREBASE
===========================

El codigo no contiene modulo de vision artificial ni endpoint para iniciarlo.
Por eso el estado es No configurada.

El firmware activo esta en firmware/ESP32_MPU6050_WIFI/ y transmite los dos
MPU6050 por HTTP/JSON. Configurar WIFI_SSID, WIFI_PASSWORD y API_URL en ese
archivo para la LAN. La API informa datos recibidos recientemente a partir
del timestamp de cada registro; el umbral de la interfaz es diez segundos.
La desconexion requiere esperar ese umbral para reflejarse.

Solo el backend usa Firebase Admin. Configurar FIREBASE_DATABASE_URL y
FIREBASE_SERVICE_ACCOUNT_FILE; por defecto la credencial es
backend/serviceAccountKey.json. La clave privada no debe versionarse. En el
nodo activo se agregan estado/modo, estado/sesion_activa, sesiones/<uuid> y
mediciones/<push-id>.

7. CONFIGURACION Y EJECUCION
============================

Backend (desde la raiz):
  py -m venv .venv
  .\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
  $env:FIREBASE_DATABASE_URL = "https://<proyecto>-default-rtdb.firebaseio.com"
  .\.venv\Scripts\python.exe backend\servidor_firebase.py

Frontend (desde frontend):
  npm install
  npm run dev

Modo simulado: en Recoleccion selecciona Simulacion antes de iniciar la
sesion. Despues de iniciar backend y frontend, desde la raiz ejecuta en otra
terminal:
  .\.venv\Scripts\python.exe backend\simulador_wifi.py
Deten Ctrl+C para parar el generador. Cierra la sesion desde la interfaz;
solo entonces puedes cambiar al modo ESP32 real. Las lecturas simuladas son
ficticias y se etiquetan; nunca indican que el hardware esta conectado.

El API escucha en 0.0.0.0:5000; Vite reenvia /api al host configurado por
VITE_API_PROXY_TARGET (frontend/.env.local; predeterminado
http://127.0.0.1:5000). Para usar ESP32, API_URL del firmware debe apuntar a
la IP LAN de la computadora, puerto 5000.
