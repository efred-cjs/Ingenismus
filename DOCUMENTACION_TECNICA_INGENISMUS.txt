1. ARQUITECTURA GENERAL
=======================

Flujo de lecturas:

  MPU6050 x 2 -> ESP32 -> HTTP/JSON por Wi-Fi -> API Flask -> Firebase
                                                    ^             |
                                                    |             v
                                  React/Vite <- GET /mediciones <-+

El ESP32 lee dos MPU6050 a traves de buses I2C independientes y manda una
solicitud POST por cada sensor. Flask valida el esquema, agrega fecha_servidor
con el timestamp de Firebase y escribe en el nodo Realtime Database
"mediciones". React consulta Flask cada dos segundos. El navegador no se
conecta directamente a Firebase; esto mantiene la credencial de servicio
exclusivamente en el backend.

3. FUNCIONAMIENTO DEL FRONTEND
==============================

El comando npm run dev sigue siendo el punto unico de inicio. La navegacion
React integra Inicio, Visualizacion, Estadisticas, Resultados, Recoleccion,
Configuracion y el menu Prueba (Pacientes promedio / Pacientes con TEA).
Las graficas representan hasta 300 registros consultados desde la API y se
actualizan con el sondeo de dos segundos. La tabla muestra la fecha del
servidor y las seis medidas de cada lectura. Los videos usan copias locales en
frontend/public/videos para que Vite los sirva sin abrir HTML independiente.

El indicador Firebase se marca conectado solo cuando GET /mediciones responde
con firebase="conectado". El estado reciente del ESP32 se calcula a partir de
timestamps de los registros y un umbral de diez segundos. Las tarjetas de
participantes y sesiones que ya aparecian en el dashboard son datos estaticos
de demostracion; no existe en este repositorio una API de pacientes/sesiones.
La interfaz los identifica como demostracion y no los mezcla con lecturas
reales.

Paleta aplicada: marino #001A41, cian #00B4FB, naranja #FF8422, coral #FA6560
y verde #436C34. La grafica se implementa en SVG, sin agregar dependencias
para Chart.js; conserva las tres series X/Y/Z, leyenda, hora y actualizacion.

4. COMO INICIAR EL FRONTEND
===========================

Desde frontend/:

  npm install
  npm run dev

En Windows PowerShell tambien se puede usar npm.cmd. Vite escucha por defecto
en el puerto 5173 y reenvia /api al backend. Para cambiar el destino del proxy,
copia frontend/.env.example a frontend/.env.local y cambia
VITE_API_PROXY_TARGET. Reinicia Vite despues de cambiarlo.

5. BACKEND, DEPENDENCIAS Y EJECUCION
====================================

Requisitos Python: 3.10 o posterior. Las dependencias activas estan en
backend/requirements.txt:

  Flask >=3.0,<4.0
  firebase-admin >=6.5,<8.0

Desde la raiz, instalar y arrancar:

  py -m venv .venv
  .\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
  .\.venv\Scripts\python.exe backend\servidor_firebase.py

En macOS/Linux, sustituir el ejecutable de Windows por .venv/bin/python.
La clave privada JSON se debe guardar localmente y no versionarse. El backend
la busca por defecto en backend/serviceAccountKey.json.

6. DIFERENCIAS ENTRE BACKENDS Y DECISION DE INTEGRACION
======================================================

El backend previo en backend/servidor_firebase.py ya era una API Firebase:
validaba los siete enteros, aceptaba sensor_id 1 o 2 y guardaba POST
/mediciones en el nodo mediciones. Tambien incluia GET /mediciones, necesario
para alimentar la interfaz, variables de entorno para Firebase y puerto, y
errores HTTP de servicio mas claros.

La version actualizada 03_servidor_wifi_firebase.py conserva el mismo esquema
POST/Firebase pero no implementa GET para el frontend, deja URL y puerto fijos
y captura errores de forma mas general. Se conservaron en backend las mejores
capacidades de ambas: POST del firmware y GET del panel, configuracion por
entorno, validacion y errores explicitos. Se amplio el limite GET a 300, que
es el historico solicitado por la interfaz original.

La otra version 03_servidor_wifi.py usa MySQL y es heredada. No se combina con
la API Firebase activa. requirements.txt en la carpeta de referencia incluye
paquetes MySQL/USB y no firebase-admin, por lo que no debe usarse para instalar
el backend activo. La aplicacion principal no tenia un receptor USB Firebase;
el flujo documentado y conservado es Wi-Fi.

7. ENDPOINTS Y CONTRATO DE DATOS
===============================

GET / devuelve estado basico de la API.
GET /mediciones?limite=N devuelve {"firebase":"conectado",
"mediciones":[...]}; N acepta 1 a 300. Registros recientes primero.
POST /mediciones espera Content-Type application/json y:

  sensor_id: entero 1 o 2
  aceleracion_x, aceleracion_y, aceleracion_z: enteros
  giroscopio_x, giroscopio_y, giroscopio_z: enteros

Una escritura correcta responde HTTP 201, ID Firebase y sensor_id. Firebase agrega
fecha_servidor como timestamp Unix en milisegundos. El firmware y simulador
usan estos mismos nombres. El proxy de Vite cambia /api/mediciones a
/mediciones en el host Flask configurado.

8. ESP32, MPU6050 Y RED
======================

El firmware activo es firmware/ESP32_MPU6050_WIFI/ESP32_MPU6050_WIFI.ino.
Usa dos buses I2C: sensor 1 SDA/SCL 21/22, sensor 2 27/26, direccion MPU
0x68. En la parte superior del .ino, configura WIFI_SSID, WIFI_PASSWORD y
API_URL con la IPv4 de la computadora y puerto 5000 (no localhost). El ESP32
y la computadora deben estar en la misma red, con acceso TCP entrante a Flask.
La computadora requiere Internet para escribir en Firebase.

Se reemplazaron los datos concretos de Wi-Fi e IP que estaban guardados en el
firmware por marcadores de configuracion. Antes de cargar el programa hay que
completar esos tres valores. No se cambio el JSON, pines, sensores ni la logica
de adquisicion.

9. FIREBASE Y VARIABLES DE ENTORNO
==================================

FIREBASE_DATABASE_URL: URL Realtime Database. Si no se define, la API conserva
la URL de proyecto que tenia el codigo.
FIREBASE_SERVICE_ACCOUNT_FILE: ruta a la clave JSON. Por defecto
backend/serviceAccountKey.json (ruta relativa a la carpeta desde donde se
inicia Python).
HTTP_PORT: puerto de Flask; predeterminado 5000.
VITE_API_PROXY_TARGET: host/puerto del backend para Vite; predeterminado
http://127.0.0.1:5000. Configurar en frontend/.env.local.
API_URL: endpoint de simulador; predeterminado
http://127.0.0.1:5000/mediciones.

El archivo raiz .env.example documenta valores sin secretos, pero Vite carga
variables desde frontend/.env.local porque npm run dev se ejecuta desde
frontend. No se incluyen credenciales Firebase en el navegador ni en estos
ejemplos.

11. VALIDACION REALIZADA Y PENDIENTE
====================================

Pruebas realizadas:
- npm run build: correcto con Vite 5.4.21; genero el bundle de produccion.
- npm run dev: Vite inicio en http://127.0.0.1:5173.
- HTTP GET a la raiz Vite: 200 y entrega index.html.
- HTTP HEAD a un video local: 200, Content-Type video/mp4 y tamano esperado.
- Los dos videos se copiaron a dist/videos al compilar.
- Sintaxis de backend/servidor_firebase.py y backend/simulador_wifi.py:
  compilacion en memoria correcta.
- Flask test client con Firebase sustituido por un stub en memoria:
  GET /, GET /mediciones, limite maximo, rechazo de cuerpo POST incompleto,
  POST correcto 201, ID y timestamp de servidor correctos.
- La credencial backend/serviceAccountKey.json no esta presente en este
  entorno; no se intento acceder a la base Firebase real.

Pruebas pendientes:
- Navegacion, selector, refresco de graficas y reproduccion verificados de
  forma interactiva en navegador; se comprobo el inicio HTTP, no se automatizo
  interaccion de navegador.
- Lectura/escritura real contra Firebase: requiere clave privada local y red.
- Lecturas del ESP32 y los dos MPU6050 fisicos: requiere hardware/red.
- Consola del navegador y flujo completo ESP32 -> Firebase -> interfaz:
  requiere la configuracion y hardware externos.

El simulador solo comprueba el flujo de prueba con datos inventados; nunca
confirma sensores fisicos. El test client usa Firebase falso en memoria y no
cuenta como una prueba de la base real.
